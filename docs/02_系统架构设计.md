## 1. 设计原则

1. **核心库是唯一的计算实现。** 信号生成、算法调用、指标计算、实验执行、结果存储全部在核心库中。Web 后端和脚本都只是核心库的调用方，Web 后端不含任何计算逻辑（NFR-07、FR-API-02）。
2. **文件是唯一的数据来源。** 实验配置和结果写成工作目录中的开放格式文件，数据库只是可重建的索引（3.5 节、NFR-43）。
3. **实验在独立子进程中运行。** Web 服务只负责交互和调度。实验进程崩溃、卡死或占满显存都不会拖垮服务；中止实验可以直接结束进程；每次运行都加载磁盘上最新的算法代码（第 6 章）。
4. **一切可扩展的东西都是插件。** 算法、阵列类型、误差类型、指标使用同一套注册和发现机制。插件自己声明参数，前端表单由声明自动生成（NFR-01~04、FR-ALG-02）。
5. **外部算法只依赖一个很小、版本独立的接口包。** 竞技场内部怎么重构，都不影响已接入的研究算法（NFR-01a）。
6. **可复现性内建于执行流程。** 随机数按固定的树状结构派生，版本信息在每次运行时自动采集，不依赖用户自觉（NFR-10、NFR-14）。

当前参考硬件（2026-11-17，需求方批准）：Windows、NVIDIA RTX 5060 Laptop GPU（8 GB）。开发验证使用独立 GPU 环境，不替换基础 Anaconda 或原 CPU 环境。

## 2. 总体架构

```
            ┌──────────────── 浏览器（React 前端）────────────────┐
            │ 实验配置  运行/结果  历史  算法库  排行榜  设置     │
            └───────────────┬─────────────────────▲──────────────┘
                     HTTP / JSON             SSE 进度推送
            ┌───────────────▼─────────────────────┴──────────────┐
            │ Web 服务（FastAPI, arena.server）                   │
            │  路由 · 任务队列 · 状态监视 · 索引维护 · 静态前端   │
            └───────┬───────────────────────────┬────────────────┘
                    │ 启动子进程                 │ 读写索引 / 读结果文件
                    │ arena run <实验目录>       │
   实验脚本 ─┐       ▼                            ▼
  (脚本模式) │  ┌──────────────────┐     ┌───────────────────────┐
   import ───┼─▶│ 核心库 arena.core │────▶│ 工作目录（文件为准）   │
   arena     │  │ 场景/算法/指标/   │写入 │ experiments/ datasets/ │
             │  │ 实验执行/存储/图表│     │ templates/ benchmarks/ │
             │  └────────┬─────────┘     │ .arena_index.sqlite    │
             │           │ 调用            └───────────────────────┘
             │  ┌────────▼──────────────────────────────┐
             └─▶│ 插件：内置算法 | 外部算法（研究项目目录）│
                │       只依赖接口包 arena_api            │
                └────────────────────────────────────────┘
```

两种模式的调用路径：

| 模式 | 路径 | 结果去向 |
|---|---|---|
| Web 模式 | 前端 → Web 服务校验配置 → 创建实验目录 → 启动子进程 `arena run` → 核心库执行 → 写文件 → 服务监视状态文件并推送进度 → 前端读取结果 | 工作目录 |
| 脚本模式 | 实验脚本 `import arena` → 调用 `arena.run(...)` 或细粒度 API → 核心库执行（在脚本进程内）→ 写文件 | 同一工作目录，Web 历史页刷新后可见 |

Web 模式的子进程执行的就是脚本模式的命令行入口，因此两条路径最终调用同一个函数 `arena.core.runner.run_experiment`。“两种模式结果逐位一致”（计算时间除外，需求 4.2 节）由结构保证，再由测试验证。

## 3. 技术选型

| 层 | 选型 | 理由 |
|---|---|---|
| 语言 / 运行环境 | Python 3.12（独立 conda 环境，建议名 `doa`） | 本机已有 Python 3.12.4、conda 24.5；PyTorch、NumPy、SciPy 生态完整 |
| 数值计算 | NumPy、SciPy | 特征分解、求根、匈牙利匹配（`scipy.optimize.linear_sum_assignment`） |
| 参数声明与配置校验 | Pydantic v2 | 参数模型可直接导出 JSON Schema，前端据此生成表单；同时负责配置校验和报错定位 |
| 学习型算法 | PyTorch（可选依赖，CUDA 版） | 需求确定；RTX 5060 Laptop（8 GB）用于推理 |
| Web 后端 | FastAPI + Uvicorn | 异步、自动生成 OpenAPI 文档、与 Pydantic 原生集成 |
| 实时进度 | SSE（Server-Sent Events） | 只需服务端单向推送，比 WebSocket 简单，断线浏览器自动重连 |
| 索引 | SQLite（Python 标准库 `sqlite3`） | 无需安装服务；只由 Web 服务进程写入 |
| 图表 | Plotly（后端生成图表描述，前端渲染） | 同一份图表描述既能在网页交互显示，也能在脚本中直接导出，两种模式图形一致（FR-RES-12） |
| 静态图导出 | Kaleido（Plotly 官方导出工具） | 导出 PDF / SVG / PNG（FR-RES-07、FR-RES-11）；Windows 兼容性需在 M3 验证（见第 13 章风险 R1） |
| 报告 | Jinja2 生成自包含 HTML；PDF 由浏览器打印生成；Word 用 python-docx（P1） | 避免在 Windows 上安装 GTK 等 PDF 渲染依赖（见 ADR-08） |
| 前端 | React 18 + TypeScript + Vite | 页面多、表单复杂、状态多，需要成熟的组件生态；类型系统便于其他 AI 接手 |
| 前端组件库 | Ant Design 5 | 中文支持好，表单、表格、折叠面板等组件齐全 |
| 动态表单 | react-jsonschema-form（`@rjsf/antd`） | 直接用后端提供的 JSON Schema 渲染参数表单，前端不写算法专用代码 |
| 前端图表 | react-plotly.js | 渲染后端给出的 Plotly 图表描述 |
| 前端数据请求 | TanStack Query | 缓存、轮询、失效管理 |
| 测试 | pytest（后端）、Vitest（前端单元）、Playwright（端到端冒烟，P1） | — |

历史环境（2026-10-29 实测，不作为当前硬件验收基准）：Windows，Python 3.12.4，conda 24.5.0，Node 24.13.1，Git 2.46.2，NVIDIA GeForce RTX 4060 Laptop GPU（8 GB，驱动 566.24）。Node 只在开发前端时需要；发布后前端是编译好的静态文件，由 Web 服务直接提供，运行时不需要 Node。

## 4. 代码仓库与包结构

### 4.1 发布包

一个 Git 仓库（monorepo），产出两个 Python 发布包：

| 发布包 | import 名 | 内容 | 依赖 |
|---|---|---|---|
| `doa-arena-api` | `arena_api` | 外部算法唯一需要依赖的接口包：插件基类、参数声明工具、数据类型（阵列描述、观测、估计结果、能力声明） | 只依赖 numpy、pydantic |
| `doa-arena` | `arena` | 核心库、内置插件、命令行、Web 服务、编译好的前端 | 依赖 `doa-arena-api`；可选组 `[torch]`、`[server]`、`[docx]` |

- `arena_api` 有独立的语义化版本号。只要主版本不变，已接入的外部算法就不需要改动（NFR-01a）。
- 只装 `doa-arena` 不装 `[server]` 时，脚本模式完全可用（FR-API-01）。
- 开发阶段两个包都以可编辑模式安装（`pip install -e`）。

## 5. 核心库设计

### 5.1 接口包 arena_api（概要）

核心数据类型：

| 类型 | 内容 | 说明 |
|---|---|---|
| `ArrayDescriptor` | 阵列类型名、阵元位置 `positions`（形状 `(M, 3)`，单位 λ）、有效阵元掩码、参数 | 算法看到的是**标称阵列**，不含误差。仅当用户设置“算法知道故障位置”时，掩码中标出故障阵元（需求 2.4） |
| `Observation` | 接收数据 `X`（`(M, N)` 复数）、信源数 `K`（可为 None）、`kind="narrowband"` | `kind` 为以后的宽带、频域数据预留 |
| `Estimate` | 角度 `angles`（一维数组 `(K̂,)`，度）、可选空间谱（网格 + 谱值）、可选附加信息字典 | 二维 DOA 只通过插件的 `dims` 声明预留，V1 不预留数组形状（NFR-05，《03_算法接口规范》12.3 节） |
| `RunContext` | 设备（`cpu` / `cuda`）、该算法专用的随机数生成器、日志器、工作目录路径 | 由 runner 提供，算法不得自己创建全局随机状态 |
| `Capabilities` | 支持的阵列类型、是否需要 K、是否处理相干信源、是否支持批量、是否可在多进程中并行、是否使用 GPU | 前端据此置灰不可用的选项（FR-ALG-05） |

算法插件的生命周期（解决“模型只加载一次”与“扫描点之间阵列可能变化”的矛盾）：

```
check(params, array, K)            类方法，校验配置时调用：静态兼容性检查，不实例化
load(params, ctx)                  每个进程一次：加载模型权重等重资源（FR-ALG-08）
configure(params, array, ctx)      参数或阵列描述变化时调用：预计算导向矢量网格
estimate(obs, ctx) -> Estimate     每次试验调用
estimate_batch(obs_list, ctx)      可选；声明支持批量时 runner 优先调用（FR-ALG-10）
close()                            实验结束时调用：释放显存等
```

```python
# 示意，完整定义见《03_算法接口规范》第 6 章
from typing import Literal
from arena_api import Algorithm, Estimate, Capabilities, ParamsModel, Param

class Music(Algorithm):
    id = "music"
    name = "MUSIC"
    version = "1.0.0"
    capabilities = Capabilities(needs_K=True, coherent="with_smoothing")

    class Params(ParamsModel):
        grid_step: float = Param(0.1, gt=0, le=5, unit="°", label="网格步长")
        smoothing: Literal["none", "forward", "fb"] = Param("none", label="空间平滑")
        subarray: int | None = Param(None, ge=2, label="子阵阵元数", none_label="自动")

    def configure(self, params, array, ctx) -> None: ...
    def estimate(self, obs, ctx) -> Estimate: ...
```

`ModelAlgorithm` 是 `Algorithm` 的子类，为学习型算法补充：模型文件参数、元数据文件读取、与当前阵列的兼容性检查（FR-ALG-06）、设备选择。学习型算法只需实现“加载网络”“预处理”“后处理”三个方法。

预留但 V1 不实现的扩展接口：
- `AdaptiveMixin.adapt(support_set)`：少样本适配 / 元学习（FR-ALG-11）。runner 将来在测试前用独立的随机数分支生成支持集并调用它。
- `RemoteAlgorithm`：把独立进程、独立 conda 环境或 MATLAB 中的算法包装成普通 `Algorithm`（FR-ALG-13）。注册表和 runner 不需要区分本地算法和远程算法。

阵列、误差、指标插件的基类同样放在 `arena_api.plugin`：
- `ArrayModel`：`positions(params) -> (M, 3)`，`steering(angles, positions) -> (M, K)`。
- `Impairment`：声明作用阶段（`positions` / `manifold` / `signal` / `output`），提供 `sample(rng, M)` 和 `apply(...)`。
- `Metric`：输入匹配后的估计与真值，输出标量或按信源的数组。

### 5.2 插件注册与发现（core.plugins）

四类插件（算法、阵列、误差、指标）共用一个注册表实现，按 `(类别, id)` 索引。

**发现来源（按顺序）：**
1. 内置插件：`arena.core.algorithms`、`arena.core.arrays` 等包内的模块。
2. Python 包入口点：已安装的包在 `pyproject.toml` 中声明 `[project.entry-points."doa_arena.plugins"]`。对应竞技场配置中 `{"type": "package"}` 来源，也用于以后把研究代码打包发布。
3. 目录来源：竞技场配置或工作目录说明中 `{"type": "path"}` 登记的目录，通常是课题仓库的 `algorithms/`（4.4 节）。注册表只看该目录的第一层：每个子目录作为一个独立的包加载，只导入其中的 `arena_plugin.py`；没有这个文件的子目录（如 `common/`）和以 `_`、`.` 开头的子目录跳过。收集入口模块中 `arena_api` 插件基类的子类。详细规则见《03_算法接口规范》10.1 节。

**规则：**
- 插件 `id` 在同类中必须唯一。外部插件与内置插件 `id` 冲突时，外部插件以 `<来源名>/<id>` 形式注册，并在算法库页提示冲突。
- 加载失败（语法错误、import 失败、缺少必需属性、参数模型无法导出 Schema）时，记录错误和堆栈，跳过该插件，继续加载其他插件（FR-ALG-01b）。
- 注册表只保存插件类，不创建实例。实例由 runner 在每次实验中创建。

**版本采集（FR-ALG-01c、NFR-14）：** 实验开始时，对每个用到的插件记录：
- 插件声明的 `version`
- 来源类型和路径
- 源文件所在 Git 仓库的 commit 哈希、是否有未提交修改（调用 `git rev-parse HEAD` 和 `git status --porcelain`，限定在该文件所在仓库）
- 有未提交修改时，把 `git diff` 输出保存为实验目录中的 `algorithm_patches/<id>.diff`，这样未提交的代码改动也能复现
- 学习型算法额外记录模型文件路径和 SHA-256 哈希

- 插件代码哈希：子目录写法时为整个算法子目录中 `.py` 文件的合并哈希（《04_数据格式规范》4.2 节）

未提交修改的检查和 `git diff` 覆盖整个课题仓库，而不只是插件所在子目录，因为插件可能 import 了 `algorithms/common/` 等其他目录中的代码。不是 Git 仓库时只记录版本、来源和代码哈希。

**脚本传入的算法对象（FR-API-04）：** 不经过注册表，runner 直接使用。来源记为 `script`，并用 `inspect.getsourcefile` 定位文件后按上述规则采集版本。

### 5.3 配置模型（core.config）

实验配置（需求 5.1）用 Pydantic 模型定义，分三层：
- **静态部分**：场景结构、实验类型、试验次数、种子、指标选择等，由核心库定义。
- **插件参数部分**：阵列参数、每个误差的参数、每个算法实例的参数。配置中按插件 `id` 引用，校验时交给对应插件的 `Params` 模型。
- **动态 Schema**：Web 服务启动时，把静态部分和所有已注册插件的 `Params` Schema 组合成完整的配置 JSON Schema，提供给前端。

**配置路径**用于参数扫描（FR-EXP 可扫描变量）和错误定位，语法为点号分隔，列表项用 `[标识]` 选择：

```
scenario.sources.snr_db
scenario.snapshots
scenario.impairments[gain_phase].params.sigma_phi_deg
algorithms[MUSIC+FBSS].params.grid_step
```

列表项标识：误差用类型 `id`，算法实例用显示名 `label`（同一实验内要求唯一）。扫描展开时，对每个取值深拷贝配置并写入该路径，再整体重新校验，所以无需为每个可扫描变量单独写代码。

**校验分两级：**
1. 结构校验（Pydantic）：类型、范围、必填项。错误带配置路径，前端据此在对应输入框旁显示（NFR-31）。
2. 语义校验：K < M、角度在范围内、算法能力与阵列匹配、学习型模型元数据与阵列匹配（只读元数据 JSON，不加载 torch）、扫描路径存在、扫描后每个取值仍然合法。

后端校验是最终依据，前端校验只用于即时提示。

### 5.4 随机数派生（core.rng）

所有随机数来自 NumPy `SeedSequence` 派生出的独立 `Generator`（PCG64），派生路径固定，不使用全局随机状态（NFR-10）：

```
SeedSequence(seed)
├── ("fixed", <误差序号>)                     固定误差实现，整个实验共用（FR-SCN-08）
├── ("trial", [<扫描点序号>], <试验序号>)
│   ├── "K"             随机信源数（K 写成分布时）
│   ├── "angles"        随机角度
│   ├── "signal"        信源波形
│   ├── "noise"         噪声
│   ├── "impairments"   每次随机的误差实现
│   └── "adapt"         预留：少样本适配的支持集
└── ("algo", <算法实例序号>, <试验序号>)       算法内部若需随机数（RunContext.rng）
```

- 每次试验的随机数只由 `(seed, 路径)` 决定，与执行顺序无关。因此多进程并行与串行结果一致（FR-EXP-10），中止后重跑同一扫描点也得到同样的数据。
- **公共随机数**：实验选项 `common_random_numbers`，默认开启。开启时路径中不含扫描点序号，不同扫描点的第 t 次试验使用同一组随机数，扫描曲线更平滑，不同扫描点之间的比较也更准确。关闭时每个扫描点独立抽样。该选项写入配置，会影响结果。
- 误差插件先抽取单位方差的随机量，再乘以强度参数。这样扫描误差强度时，固定误差的“形状”保持不变，只改变大小。
- 同一次试验的数据只生成一次，所有算法共用（FR-EXP-02）。

### 5.5 场景与试验数据生成（core.scenario、core.signals）

`sample_trial` 由场景配置和该次试验的随机数生成一次试验的全部数据。runner 和数据集生成（FR-GEN）都调用这个函数，所以训练数据与测试数据同分布（FR-GEN-01）。

```
sample_trial(scenario, rngs, fixed) -> TrialData
 1. 角度：固定值，或在范围内随机（拒绝采样，保证最小间隔）
 2. 阵元位置：标称位置 + 位置误差                 [误差阶段 positions]
 3. 真实流形：A = steering(θ, 实际位置)，再左乘 Γ、C [误差阶段 manifold]
 4. 信源：按功率和相关系数矩阵生成 S（Cholesky；相干时用特征分解）
 5. 无噪数据：A·S；故障阵元（仅含噪声模式）信号行置零 [误差阶段 signal]
 6. 加噪声 W（σ_n² = 1，信源功率 = 10^(SNR/10)）
 7. 故障阵元（置零模式）整行置零                     [误差阶段 output]
 → TrialData(X, 真值角度, K, 标称 ArrayDescriptor, 本次误差实现, SNR 等标签)
```

误差插件声明自己的作用阶段，`sample_trial` 按阶段顺序调用，顺序与需求 2.4 节一致。新增误差类型只需声明阶段，不修改 `sample_trial`（NFR-03）。

### 5.6 实验执行（core.runner）

入口 `run_experiment(config, workspace, mode)`。配置中的算法实例可以是已登记算法的 `id`，也可以是脚本中用 `Algorithm.spec()` 传入的未登记算法类（FR-API-04）。三种实验类型统一处理：单次实验 = 1 个扫描点 × 1 次试验，蒙特卡罗 = 1 个扫描点 × T 次试验，参数扫描 = P 个扫描点 × T 次试验。

```
0. 校验配置；创建实验目录（Web 模式下由服务预先创建，这里复用）
   写 config.json、meta.json（status = running）
1. 解析插件，采集版本信息 → meta.json
2. 实例化所有算法实例，调用 load(ctx)；失败的算法标记为不可用，其余继续
3. 对每个扫描点 p：
   a. 展开该点的配置；参数或阵列变化的算法调用 configure()
   b. 按块（默认每块 64 次试验）生成试验数据
   c. 对每个算法：支持批量则 estimate_batch，否则逐次 estimate
      每次调用：计时 → 校验输出 → 记录估计值或错误
   d. 该点全部完成后：匹配、计算指标和 CRB
   e. 写 points/p_<序号>.npz，更新 summary.json、errors.json 和 status.json
   f. 每块之间检查是否收到取消请求
4. 所有算法调用 close()
5. 合并各扫描点结果 → results.npz，然后删除 points/
   status = completed / cancelled / failed
   （.mat、CSV 等按需导出，不在这里生成，见《04_数据格式规范》4.7 节）
```

**出错隔离（FR-ALG-09）：**
- 每次调用都包在异常捕获中。异常、输出形状不对、包含 NaN/Inf、角度超出范围，都记为该次试验的错误，并保存错误类型和第一次出现时的堆栈。
- 出错的试验在成功率中算作失败，在 RMSE 中按需求 2.5 节的规则处理（估计数不等于 K）。
- 同一算法在某个扫描点连续 20 次出错（阈值可配置）时，跳过该点剩余试验并标记，避免一个坏算法拖慢整个实验。
- `load` 或 `configure` 失败只影响该算法，结果中显示失败原因。

**计时（需求 2.5 节）：**
- 用 `time.perf_counter` 只包住 `estimate` 调用，不包含数据生成。
- 预热：每个算法在每个扫描点开始前，用该点第一次试验的数据额外调用一次 `estimate`，结果丢弃、不计时（排除 CUDA 初始化、缓存等一次性开销）。预热是额外调用，不占用试验，所以单次实验（T = 1）也有耗时数据。
- 声明使用 GPU 的算法，计时结束前由 runner 调用 `torch.cuda.synchronize()`（runner 只在实验中有 GPU 算法时才 import torch）。
- 批量调用的耗时按批大小均摊，结果中标记为“批量均摊”。
- 结果中同时记录运行设备。

**并行（FR-EXP-10）：** 选项 `workers`，默认 1。大于 1 时，试验块分发给进程池（Windows 使用 spawn 方式），每个工作进程在初始化时加载插件并调用一次 `load()`。声明 `parallel_safe=False` 或使用 GPU 的算法始终在主进程中运行。由于随机数只由路径决定（5.4 节），并行结果与串行一致。并行时 CPU 争用会使计时偏大，结果中会标记“并行运行，计时仅供参考”。需要严格对比耗时的实验应使用 `workers=1`。

**进度与取消：**
- `status.json` 采用“写临时文件再重命名”的原子写法，最多每 0.5 秒写一次，内容包括：状态、当前扫描点、已完成 / 总试验数、预计剩余时间、心跳时间、进程号。
- 取消请求：Web 模式下由服务在实验目录中创建 `CANCEL` 文件；脚本模式下按 Ctrl+C。runner 在块之间检查，收到后完成当前块、写出已完成的扫描点，状态记为 `cancelled`（FR-EXP-06）。
- 服务发出取消请求 10 秒后若进程仍未退出（例如卡在某次 `estimate` 中），直接结束进程，再调用 `storage.finalize(实验目录)`，把已写出的扫描点合并为结果。
- 进程异常退出时状态停留在 `running`，但心跳停止。心跳超过 30 秒未更新且进程不存在时，索引将其显示为 `interrupted`，用户可以把已完成部分整理为结果。

实验状态取值：`queued`、`running`、`completed`、`cancelled`、`failed`、`interrupted`。

### 5.7 指标与 CRB（core.metrics、core.crb）

**匹配**：每次试验用 `scipy.optimize.linear_sum_assignment` 对 K×K̂ 的绝对误差矩阵求最小总代价配对（需求 2.5 节）。K 很小，逐次求解即可，1000 次试验耗时可以忽略。匹配结果整理为 `MatchedSet`（配对误差、各次估计数、真值），作为所有指标插件的统一输入。

**指标由原始估计重新计算**：runner 保存每次试验的原始估计值（NaN 填充为 `(T, K_max)`）和估计数。指标总是从原始估计算出，因此修改成功门限等指标参数后，可以不重跑实验，直接重新计算（`arena.recompute_metrics`，FR-DAT-06）。

**随机 CRB**（Stoica & Nehorai 1990）：

```
CRB(θ) = σ_n² / (2N) · { Re[ (D^H P_A^⊥ D) ⊙ (P A^H R^{-1} A P)^T ] }^{-1}
D = [∂a(θ_1)/∂θ_1, …, ∂a(θ_K)/∂θ_K],  P_A^⊥ = I − A(A^H A)^{-1}A^H
```

- 用标称阵列、真实信源协方差 P（含相关性）和理论协方差 R = A P A^H + σ_n² I 计算，结果从弧度换算为度。
- 导向矢量的导数由阵列插件提供（`ArrayModel.steering_derivative`）；未提供时用数值差分，结果中标明。
- 角度随机时，对每次试验的 CRB 取平均后再开方，与 RMSE 的统计方式一致。
- A 列不满秩（如两个角度重合、K ≥ M）时，返回 NaN 并给出警告，不中断实验。
- 结果同时给出每个信源的 CRB 和平均值。

### 5.8 结果存储与索引（core.storage）

**实验目录命名**：`YYYYMMDD-HHMMSS_<名称缩写>_<4位随机码>`。名称缩写只保留 ASCII 字母、数字和连字符（避免 Windows 路径问题），中文名称完整保存在 `meta.json` 中。实验 ID 就是目录名。

**目录内文件**（字段定义见《04_数据格式规范》）：

| 文件 | 写入者 | 内容 |
|---|---|---|
| `config.json` | runner | 完整配置，已填入全部默认值 |
| `meta.json` | runner | 名称、时间、运行模式、状态、竞技场与 `arena_api` 版本、插件版本、模型哈希、运行环境 |
| `status.json` | runner | 运行中的进度和心跳 |
| `points/p_XXX.npz` | runner | 每个扫描点的原始估计、错误、计时、指标；正常结束或取消后合并进 `results.npz` 并删除，只在运行被中断时留下，用于整理部分结果 |
| `results.npz` | runner | 合并后的完整结果。`.mat`、CSV 等按需导出到 `exports/` |
| `summary.json` | runner | 指标汇总（小文件，供列表、排行榜和快速查看） |
| `errors.json` | runner | 错误汇总，同一种错误只保存第一次的堆栈 |
| `notes.json` | Web 服务 / API | 备注和标签。与 runner 写的文件分开，运行中也可以编辑 |
| `algorithm_patches/*.diff` | runner | 未提交的算法代码改动 |
| `log.txt` | runner | 日志和错误堆栈 |

**写入规则**：所有 JSON 和 npz 都先写临时文件再重命名，进程中断时不会留下写了一半的文件。结果文件不使用 pickle（NFR-44）。

**索引**（`.arena_index.sqlite`，位于工作目录根部）：
- 只有 Web 服务进程写入索引。runner 和脚本只写实验目录，从不碰索引，因此两种模式可以同时使用同一工作目录（FR-SYS-05）。
- 列表请求到来时，服务比较目录列表和各目录中 `meta.json`、`notes.json`、`summary.json` 的修改时间，只重新读取有变化的目录，然后更新索引。数千个实验时这一步也在毫秒到百毫秒量级。
- 索引表保存列表和筛选需要的字段：ID、名称、创建时间、运行模式、状态、实验类型、扫描变量、算法列表、标签、场景集评测 ID。
- 删除索引文件后，服务启动时全量扫描重建（FR-DAT-01a）。命令行 `arena index rebuild` 也可以手动重建。

**删除**：移动到工作目录内的 `.trash/`（FR-DAT-05），可在设置页清空。

**模板**：用户模板保存在 `<工作目录>/templates/scenario/` 和 `templates/experiment/` 下，每个模板一个 JSON 文件；内置模板随软件发布，只读。

**工作目录初始化**：首次使用时生成 `arena_workspace.json` 和建议的 `.gitignore`（忽略索引、`.trash/`、`*.npz`、`*.mat`、`datasets/`），用户可自行修改。

### 5.9 图表、导出与报告（core.figures）

- **图表构建**：`build_figure(result, kind, style)` 返回 Plotly 图表对象。`kind` 包括空间谱、指标曲线（RMSE + CRB、成功率、分辨概率、耗时）、估计值散点 / 直方图。Web 服务把它序列化为 JSON 交给前端渲染；脚本模式直接显示或导出。两种模式使用同一个函数，图形一致（FR-RES-12）。
- **样式预设**：`interactive`（网页默认）、`paper`（单栏论文：衬线字体、线宽、标记、黑白可区分的线型）、`paper-double`（双栏）。用户可在预设基础上覆盖单项（FR-RES-10）。
- **静态导出**：Kaleido 导出 PDF / SVG / PNG（PNG 按 300 dpi 等效尺寸）。
- **数据导出**：CSV（每个指标一张表）、`.mat`（`scipy.io.savemat`，字段名只用 MATLAB 合法标识符）。
- **LaTeX 表格**：指标汇总表生成 `tabular` 代码（booktabs 风格，最优值可加粗），FR-RES-11。
- **报告**：Jinja2 模板生成自包含 HTML（图表内嵌为 SVG，配置摘要和指标表为 HTML 表格），不依赖网络和竞技场即可打开。PDF：Web 端用浏览器打印（报告页带打印样式）；脚本模式若安装了 Playwright 可直接输出 PDF，否则只输出 HTML。Word（P1）用 python-docx，图表插入 PNG。

### 5.10 数据生成接口（core.datasets，FR-GEN）

- **数据集配置**：在场景配置基础上，数值参数可以写成分布，如 `{"uniform": [-10, 20]}`、`{"choice": [1, 2, 3]}`，K 可变，角度随机且满足最小间隔（FR-GEN-02）。
- **生成**：第 i 个样本的随机数路径为 `("sample", i)`，调用同一个 `sample_trial`（5.5 节），输出 X 或样本协方差 R̂ 以及全部标签（FR-GEN-01）。由于每个样本只由 `(seed, i)` 决定，可以并行生成、分片生成，也可以只生成其中一段。
- **落盘**：npz 分片（默认每片 1 万个样本），每个样本默认保存 R̂（可选 X 或两者），以 float32 / complex64 存储；附带 `dataset.json`，其中记录生成配置、种子、样本数、竞技场版本和 `arena_api` 版本（FR-GEN-04）。变长的角度标签用 NaN 填充到 K_max，并单独保存 K。字段见《04_数据格式规范》第 5 章。
- **在线生成**：`arena.datasets.TorchDataset(config, size, seed)` 的 `__getitem__(i)` 即时生成第 i 个样本，可配合多个 DataLoader worker 使用，不占磁盘，结果仍然可复现（FR-GEN-05）。
- **网格标签**：`grid_labels(angles, grid, sigma=None)` 生成多标签向量或高斯平滑标签。网格定义与学习型模型元数据中的 `output.grid` 使用同一种写法（FR-GEN-03）。
- 数据生成只依赖 numpy、scipy、pydantic 和 `arena_api`，不依赖 Web 服务和 torch（`TorchDataset` 除外），可以在没有显示器的 Linux 云服务器上运行（见第 9 章）。

### 5.11 标准场景集与排行榜（core.benchmark，FR-BEN）

- 场景集是一个带版本号的 JSON 文件（`suite_id`、`version`、若干带名称的实验配置，种子固定）。内置场景集随软件发布在 `arena/benchmarks/`；用户自定义场景集放在 `<工作目录>/benchmarks/suites/`。
- 运行场景集：对选定的算法逐个运行其中的实验配置，生成普通实验目录，`meta.json` 中记录 `benchmark = {suite_id, version, run_id, scenario_name}`。
- 排行榜由各实验的 `summary.json` 汇总而成，不单独存一份结果，所以不会与实验文件不一致。只有同一 `suite_id` + `version` 的结果参与同一排行（FR-BEN-04）。同一算法在同一场景有多次运行时，默认取最新一次，并显示其 commit，可切换为指定版本（FR-BEN-05）。

### 5.12 脚本模式门面（arena 顶层）

```python

# 完整实验：配置文件 / 字典 / 配置对象均可（FR-API-02）

# 传入调试中的算法对象，无需登记（FR-API-04）

# 细粒度调用（FR-API-03）
```

`arena.run` 在调用进程内执行（不启动子进程），所以可以直接调试算法、设断点。

## 6. Web 服务设计（arena.server）

### 6.1 进程模型

```
arena serve
  └─ Web 服务进程（FastAPI + Uvicorn，监听 127.0.0.1:8765）
       ├─ 任务队列（内存中，FIFO，同时只运行一个，FR-EXP-08）
       └─ 子进程：python -m arena run <实验目录>   ← 每个实验一个，结束即退出
```

- 服务进程只 import 核心库的配置、插件元信息、存储和图表模块，**不 import torch**。插件只做发现和读取声明，不实例化。启动快，内存小。
- 实验子进程使用与服务相同的 Python 解释器（`sys.executable`），由核心库完成全部计算，结束后释放所有内存和显存。
- 每次实验都在新进程中重新加载插件，所以修改外部算法代码后直接重新运行即可，不需要重启服务。算法库页的“刷新”只重新读取插件声明。
- 队列不持久化。服务重启时，状态仍为 `queued` 的实验目录标记为 `cancelled`，可在历史页重新提交。
- `arena serve` 启动后自动打开浏览器（FR-SYS-01）。

### 6.2 HTTP 接口概要

完整定义由 FastAPI 自动生成 OpenAPI 文档（`/docs`），这里只列资源划分：

| 资源 | 主要接口 |
|---|---|
| 插件 | `GET /api/plugins`（列表、来源、版本、加载错误）· `GET /api/plugins/{kind}/{id}/schema` · `POST /api/plugins/refresh` |
| 配置 | `GET /api/schema/experiment`（组合后的完整 Schema）· `POST /api/config/validate`（返回带配置路径的错误列表）· `POST /api/config/preview`（阵列几何和信源示意数据，FR-SCN-11）· `POST /api/config/estimate-cost`（总运行次数，FR-EXP-04）· `POST /api/config/to-script`（FR-API-06） |
| 实验 | `POST /api/experiments`（提交）· `GET /api/experiments`（列表与筛选）· `GET /api/experiments/{id}` · `POST /api/experiments/{id}/cancel` · `POST /api/experiments/{id}/rerun` · `DELETE /api/experiments/{id}` · `PATCH /api/experiments/{id}/notes` |
| 进度 | `GET /api/experiments/{id}/events`（SSE）· `GET /api/jobs`（队列，含脚本模式正在运行的实验） |
| 结果 | `GET /api/experiments/{id}/figures/{kind}`（Plotly JSON）· `GET /api/experiments/{id}/summary` · `POST /api/experiments/{id}/recompute`（修改指标参数后重新计算） |
| 导出 | `GET /api/experiments/{id}/export/{format}`（csv / mat / pdf / svg / png / tex / html / docx） · `POST /api/compare/figure`（多实验叠加，FR-RES-09） |
| 模板 | `GET/POST/DELETE /api/templates/{kind}` |
| 场景集与排行榜 | `GET /api/benchmarks` · `POST /api/benchmarks/{suite}/run` · `GET /api/leaderboard` |
| 设置与系统 | `GET/PUT /api/settings` · `GET /api/workspaces` · `PUT /api/workspaces/current` · `GET /api/system`（版本、CUDA，FR-SYS-02） · `GET /api/logs` |

### 6.3 进度推送

- `watcher` 每 0.5 秒读取正在运行的实验的 `status.json`，有变化时通过 SSE 推送给订阅该实验的前端。
- 扫描点完成时推送 `point_done` 事件，前端随即重新请求图表，曲线逐点出现（FR-EXP-07）。
- 脚本模式的实验也写 `status.json`，因此在 Web 端同样能看到进度，只是不能从 Web 端取消（只能在脚本中 Ctrl+C）。

### 6.4 安全

- 默认只监听 `127.0.0.1`，不对局域网开放（需求：单用户本机）。
- 所有涉及文件路径的接口只接受实验 ID、模板名等标识，由服务解析为工作目录内的路径，并检查结果确实位于工作目录之内，防止路径穿越。
- 外部算法是用户自己的代码，以用户权限运行，竞技场不做沙箱隔离。这一点在算法接入指南中说明：只登记自己信任的目录。

### 7.2 动态表单

- 前端启动时请求 `/api/schema/experiment`，得到包含全部插件参数的 JSON Schema。阵列参数、误差参数、算法参数表单全部由 `@rjsf/antd` 按 Schema 渲染，前端没有任何针对具体算法或阵列的代码（FR-ALG-02、FR-SCN-12）。

- 编辑过程中，前端按 300 ms 防抖调用 `/api/config/validate`，把带配置路径的错误显示在对应输入框旁。

### 7.3 状态与数据

- 服务端数据（插件、实验列表、结果）用 TanStack Query 管理。当前正在编辑的实验配置保存在页面状态中，并自动存入浏览器本地存储，刷新页面不会丢失。
- 图表由后端返回 Plotly JSON，前端只负责渲染和交互（缩放、悬停、图例显隐，FR-RES-06）。前端不做任何指标计算。

### 7.4 构建与发布

- 开发时：`npm run dev`，Vite 开发服务器把 `/api` 代理到 `127.0.0.1:8765`。
- 发布时：`npm run build` 的产物复制到 `arena/server/static/`，由 FastAPI 直接提供。用户运行 `arena serve` 即可使用，不需要 Node。

## 9. 云端训练与本机评测的衔接

需求方的学习型模型在 AutoDL 等云 GPU 平台（Linux）上训练，训练好的模型下载到本机（Windows，RTX 5060 Laptop）推理和测试。竞技场不直接连接云平台，但要保证两端使用的信号模型一致，并让模型能可靠地从云端带回本机。

### 9.1 流程

```
本机                                   云平台（AutoDL，Linux）
───────────────────────────────        ───────────────────────────────────
课题仓库 fewshot-doa：算法插件、        git clone 课题仓库 fewshot-doa
网络结构、训练脚本、                    pip install doa-arena-api doa-arena（不带 [server]）
数据集配置  ── git push ──────────▶    训练脚本：
                                         arena.datasets.TorchDataset（在线生成）
                                         或 arena dataset generate（离线生成）
                                         import 研究项目中的网络定义 → 训练
                                         arena.models.export(...) → 模型包
fewshot-doa/arena_ws/models/ ◀── 下载 ── 模型包（目录或 zip）
arena model import → 校验
Web / 脚本中选择该模型 → 评测
```

### 9.2 训练与评测分别依赖什么

训练过程本身（网络、损失函数、优化器、训练循环）是普通的 PyTorch 代码，**不需要实现竞技场的任何接口**。训练脚本只在两处可选地调用竞技场：生成训练数据、导出模型包。本机评测时，竞技场通过算法插件调用模型。

| 环节 | 运行位置 | 是否依赖竞技场 | 依赖的内容 |
|---|---|---|---|
| 网络结构定义（`nn.Module`） | 研究项目代码 | 否 | 纯 PyTorch。训练脚本和算法插件 import 同一份定义 |
| 训练循环、损失、优化器 | 云端 | 否 | 纯 PyTorch，竞技场不介入 |
| 训练数据生成 | 云端 | 推荐使用，不是强制 | `arena.datasets`。用它才能保证训练与测试的信号模型一致（FR-GEN） |
| 导出模型包 | 云端 | 推荐使用，不是强制 | `arena.models.export`。也可以手工保存 `state_dict` 并写 `model.json`，只是要自己填写版本和哈希 |
| 推理评测 | 本机 | 是 | 研究项目中的算法插件（`ModelAlgorithm` 子类）：加载权重、预处理、调用网络、后处理 |

课题仓库中的代码组织（完整结构见 4.4 节）：

```
fewshot-doa/                                （GitHub 仓库）
├── algorithms/cnn_grid/
│   ├── net.py              网络结构：纯 PyTorch，不依赖竞技场
│   ├── train.py            训练脚本：from algorithms.cnn_grid.net import CnnGrid；
│   │                       调用 arena.datasets、arena.models.export
│   └── arena_plugin.py     算法插件：继承 arena_api.ModelAlgorithm，from .net import CnnGrid
├── configs/datasets/train_k1-3.yaml        训练数据集配置
└── arena_ws/                               工作目录，已登记 ../algorithms
```

云端在课题仓库根目录运行 `python -m algorithms.cnn_grid.train --dataset configs/datasets/train_k1-3.yaml`。训练脚本和插件 import 同一个 `net.py`，网络结构只有一份。

如果某次训练用的是自己写的数据生成代码，竞技场仍然可以评测这个模型，只是 FR-GEN-08 的信号模型一致性检查无法进行，结果页会提示“训练数据来源未知”。

### 9.3 云端安装

- 研究项目仓库与竞技场仓库都托管在 GitHub（A4）。云端用 `git clone` 获取研究项目，用 `pip install "doa-arena-api @ git+https://github.com/<用户>/doa-arena#subdirectory=packages/arena_api"` 和 `doa-arena`（同理）安装竞技场核心库，并在训练脚本的依赖文件中固定竞技场的版本标签。仓库为私有时，云端使用 GitHub 个人访问令牌（只授予读权限）。云端访问 GitHub 不畅时，在本机 `python -m build` 出 wheel，上传后安装。
- **不能替换云端镜像中的 PyTorch。** `doa-arena` 的核心依赖不包括 torch，`[torch]` 可选组也不锁定版本，云端直接使用镜像自带的 PyTorch 和 CUDA。
- 核心库和数据生成必须在 Linux 上可用：路径一律用 `pathlib`，不调用 Windows 专有接口，没有图形界面依赖。测试在 Windows 和 Linux 上都要通过（见第 11 章）。

### 9.4 信号模型一致性

训练数据在云端生成，测试数据在本机生成。为了发现两端版本不一致的情况：
- 核心库定义常量 `GENERATOR_VERSION`。只要 `sample_trial` 的语义发生变化（误差作用顺序、SNR 定义、角度定义等需求第 2 章的内容），就递增这个版本号。仅修改性能或代码结构时不递增。
- `dataset.json` 和模型元数据 `model.json` 都记录：竞技场版本、`GENERATOR_VERSION`、完整的数据集配置（内嵌，不只是云端路径）。
- 本机评测时比较模型的 `GENERATOR_VERSION` 与当前竞技场的版本，不一致时在结果页明确提示“训练数据的信号模型版本与当前不同”。同时用内嵌的数据集配置判断测试条件是否超出训练范围（FR-GEN-06）。

### 9.5 模型包格式

```
cnn_grid_m16_v3/
├── model.pt        # 只保存 state_dict（权重），不保存整个模型对象
├── model.json      # 元数据：需求 5.2 节字段 + 下列追加字段
└── train_log/      # 可选：训练曲线等，竞技场只展示不解析
```

`model.json` 追加字段：插件 `algorithm_id`、竞技场版本、`arena_api` 版本、`GENERATOR_VERSION`、内嵌的训练数据集配置、训练代码仓库的 commit、PyTorch 版本、训练用 GPU、创建时间、`model.pt` 的 SHA-256。

设计要点：
- **网络结构代码不进入模型包**，它属于研究项目中的算法插件，由 Git 管理。模型包只带权重。原因：保存整个模型对象依赖 pickle，代码目录一变就无法加载，而且加载 pickle 有执行任意代码的风险。加载时使用 `torch.load(path, map_location=device, weights_only=True)`。
- 评测时比较 `model.json` 中训练代码的 commit 与当前插件的 commit，不同时提示（不阻止，因为网络结构可能没变）。权重与网络结构不匹配时，`load()` 报错并显示 PyTorch 给出的缺失 / 多余参数名。
- 云端 GPU 与本机 GPU 不同，推理结果允许有浮点级差异（需求 FR-SCN-09 已允许）。8 GB 显存只用于推理，对 V1 的示例模型足够。

### 9.6 竞技场中的支持

| 功能 | 说明 | 优先级 |
|---|---|---|
| `arena.models.export(state_dict, metadata, out_dir)` | 训练脚本调用，写出模型包并自动补齐版本、哈希、数据集配置等字段（FR-GEN-09） | P0 |

## 10. 非功能需求的实现方式

| 需求 | 实现方式 |
|---|---|
| NFR-20 性能（1000 次 × 5 算法 < 1 分钟） | 谱峰类算法在 `configure()` 中预计算整个网格的导向矢量矩阵（16 × 1801），每次估计只做矩阵乘法和一次 16×16 特征分解。粗略估算单次调用在亚毫秒量级，串行即可满足目标。M1 结束时用基准测试实测，不满足再启用并行 |
| NFR-21 界面响应 | 计算全部在子进程中；服务端只读小文件（`summary.json`、`status.json`）；图表按需生成并缓存 |
| NFR-22 存储大小 | 默认只保存单次实验的空间谱和接收数据；逐次估计按 float64 存储（保证逐位比较），7 点 × 1000 次 × 6 算法 × 3 信源约 3 MB（《04_数据格式规范》4.5 节） |
| NFR-10、NFR-14 可复现 | 5.4 节随机数派生树；5.2 节版本采集；配置写入时填满默认值，以后修改默认值也不影响旧实验重跑 |
| NFR-11~13 正确性 | 第 11 章测试 |
| NFR-23 GPU | 学习型插件默认 `device="cuda"`，无 CUDA 时自动回退 CPU 并在结果中记录；GPU 选项是否可用由 `/api/system` 提供（服务进程通过 `nvidia-smi` 或在子进程中检测，避免服务进程 import torch） |
| NFR-40 环境 | 依赖用 `pyproject.toml` 声明；README 给出 conda 环境创建命令和 CUDA 版 PyTorch 安装命令（安装时按 PyTorch 官网当时的命令为准，需支持本机 Blackwell 架构） |
| FR-SYS-05 两种模式共存 | 只有服务进程写索引；runner 只写自己的实验目录（5.8 节） |

## 13. 架构决策记录（ADR）

| # | 决策 | 考虑过的方案 | 理由 |
|---|---|---|---|
| ADR-01 | 以核心库为中心，Web 后端只是调用方 | 以 Web 后端为中心，脚本通过 HTTP 调用 | 脚本模式不需要启动服务，可以直接设断点调试算法；两种模式共用一份实现，结果一致由结构保证 |
| ADR-02 | 每个实验在独立子进程中运行 | 服务进程内的线程；Celery + Redis | 线程无法强制中止卡死的算法，GIL 也限制并行；Celery 需要额外安装 Redis，对单用户本机来说太重。子进程可以直接结束，结束后显存全部释放，每次运行都加载最新的算法代码 |
| ADR-03 | 文件为唯一数据来源，SQLite 只做可重建索引，只由服务进程写 | 结果全部存数据库 | 需求方要求结果能纳入 Git / EXP 数据管理（Q11）；只有一个写入者，避免两种模式同时运行时锁冲突 |
| ADR-04 | 插件参数用 Pydantic 声明，导出 JSON Schema 生成前端表单 | 自定义参数描述格式；前端手写表单 | 校验、默认值、Schema 一处定义；前端零改动接入新算法（NFR-01） |
| ADR-05 | 图表由后端用 Plotly 生成，前端只渲染 | 前端用 ECharts 自己画；后端用 Matplotlib 出图 | 同一份图表描述同时服务于网页交互和脚本导出（FR-RES-12）；指标计算不出现在前端 |
| ADR-06 | `SeedSequence` 按路径派生随机数，默认公共随机数 | 每个扫描点一个种子顺序抽取 | 结果与执行顺序无关，并行、中止重跑都能复现；公共随机数使扫描曲线更平滑 |
| ADR-07 | V1 外部算法与竞技场同进程运行（Q12） | 每个算法一个独立进程 / 环境 | 实现简单、调用开销为零；代价是外部算法必须能在竞技场的 conda 环境中 import。预留 `RemoteAlgorithm` 适配器以后解决环境冲突 |
| ADR-08 | 报告用自包含 HTML，PDF 走浏览器打印 | WeasyPrint；LaTeX 编译 | WeasyPrint 在 Windows 上需要安装 GTK；LaTeX 编译依赖本机 TeX 环境且出错难排查 |
| ADR-09 | 模型包只存 state_dict，网络结构留在插件代码中 | 保存整个模型对象；导出 ONNX / TorchScript | 不依赖 pickle，加载安全；网络结构由 Git 管理。ONNX / TorchScript 可作为以后的可选格式 |
| ADR-10 | 前端用 React + TypeScript + Ant Design | Vue 3；Streamlit / NiceGUI 等纯 Python 界面 | 纯 Python 界面难以实现多页面、复杂动态表单和实时进度；React 生态中 JSON Schema 表单和 Plotly 组件最成熟，交给其他 AI 开发时资料也最多 |

## 14. 风险

| # | 风险 | 应对 |
|---|---|---|
| R1 | Kaleido 在 Windows 上导出静态图可能出现兼容问题（新版本依赖本机安装的 Chrome） | M3 首先在本机验证；不行时改用固定的旧版本，或用 Matplotlib 单独实现“论文样式”导出 |
| R2 | 本机工作路径含中文（如 `D:\01_工作\...`），部分工具对非 ASCII 路径支持不好 | 实验目录名只用 ASCII（5.8 节）；M1~M3 的测试在含中文的路径下运行一遍 |
| R3 | Windows 多进程使用 spawn 方式，脚本模式开并行时用户脚本必须有 `if __name__ == "__main__":` 保护 | 在脚本模式指南和示例中写明；未保护时给出明确报错 |
| R4 | 外部算法的依赖与竞技场冲突（同进程，ADR-07） | 接入指南要求外部算法依赖装在同一环境；冲突严重时启用 `RemoteAlgorithm`（P2） |
| R5 | 工作目录放在 OneDrive 等同步文件夹中，同步进程会锁文件，影响 SQLite 和原子重命名 | 设置页检测并提示；建议把工作目录放在非同步目录 |
| R6 | Pydantic 生成的某些 Schema 结构（可选类型、联合类型）在 rjsf 中显示不友好 | 服务端对 Schema 做一层后处理；在接口规范中限定插件参数可用的类型 |
| R7 | 云端与本机竞技场版本不一致，导致训练和测试的信号模型不同 | `GENERATOR_VERSION` 检查（9.4 节）；训练脚本固定竞技场版本 |
| R8 | `scipy.io.savemat` 写含中文的字符串时，MATLAB 无法加载整个 `.mat` 文件（2026-10-29 本机 MATLAB R2024a 实测） | 导出时把字符数据写成 UTF-16，已实测可行；含中文的 `.mat` 样例列入测试（《04_数据格式规范》4.7 节） |
