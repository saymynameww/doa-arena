## 1. 一句话说清楚

**竞技场是一个让各种 DOA 估计算法在同一套仿真条件下公平比较的工具。** 你只写算法本身，信号生成、阵列误差、指标计算、CRB、画图、存档都由竞技场完成。

它在你的研究流程中的位置：

```
IDEA 选题与立项          EXP 研究执行                    PAPER 论文写作
Zotero / Obsidian   →   竞技场：评测、对比、出图    →   LaTeX
                        课题仓库：算法、训练脚本
                        云端：训练学习型模型
```

## 2. 它解决什么问题

| 以前的做法 | 竞技场的做法 |
|---|---|
| 每个算法的实验脚本各自生成数据，性能差异说不清是算法造成的还是数据造成的 | 所有算法用同一份接收数据，信号和误差模型只有一套实现 |
| 学习型模型的训练数据和测试数据用不同代码生成，两边可能悄悄不一致 | 云端训练脚本调用竞技场的数据生成接口，与本机测试用同一套模型；版本不一致时自动提示 |
| 每接入一个算法都要重写数据加载、指标、画图 | 算法只实现“输入接收数据，输出角度”，其余全部自动完成 |
| 过几个月就不记得某张图是用哪版代码、什么参数跑的 | 每次实验自动记录配置、随机种子、代码 commit，连未提交的改动也保存下来 |
| 论文出图要手工整理数据 | 一键导出 PDF 矢量图、LaTeX 表格、`.mat`、CSV |

## 3. 你会怎么用它

**三种用法，背后是同一个计算核心：**

| 用法 | 适合做什么 | 举例 |
|---|---|---|
| 网页 | 调参、快速看效果、单次对比 | 打开浏览器，选场景和算法，点“运行”，看曲线 |
| Python 脚本 | 系统实验、批量跑、论文图的可复现生成 | `scripts/run_fig3.py` 里写好配置，一条命令跑完 |
| 云端训练脚本 | 在 AutoDL 上生成训练数据、导出模型 | 训练脚本调用 `arena.datasets` 生成数据 |

网页和脚本跑出的实验存到同一个地方，可以在网页上统一查看、对比、导出。同一个配置无论从哪里运行，结果都逐位相同（计算时间除外）。

**一个典型的研究循环：**

1. 在课题仓库里写新算法 B（一个 `arena_plugin.py` 文件）。
2. 网页上刷新，B 出现在算法列表里，和 MUSIC、ESPRIT 一起跑几个场景，看看效果。
3. B 是学习型算法时：把代码推到 GitHub，在 AutoDL 上训练，下载模型包，导入竞技场。
4. 效果满意后，写脚本跑论文需要的全部扫描实验。
5. 导出 PDF 图放进论文目录，`README` 里记下实验 ID。

详见：需求第 7 章“典型使用流程”，原型第 10 节。

## 4. 系统由哪几块组成

```
   浏览器（网页界面）            你的 Python 脚本 / 云端训练脚本
          │                                  │
          ▼                                  │
   Web 服务（只负责交互和调度，不做计算）     │
          │ 每个实验启动一个独立进程           │
          ▼                                  ▼
 ┌──────────────── 核心库（唯一的计算实现）────────────────┐
 │ 场景与信号生成 · 阵列误差 · 实验执行 · 指标与 CRB ·      │
 │ 结果存储 · 图表与导出 · 训练数据生成                     │
 └──────────────┬────────────────────────────┬────────────┘
                │ 通过接口包调用               │ 写文件
                ▼                            ▼
   算法插件（内置基线 + 你课题仓库里的算法）    工作目录（实验结果、数据集、模型包）
```

| 模块 | 作用 | 你需要关心的程度 |
|---|---|---|
| 接口包 `arena_api` | 规定算法插件怎么写。很小，版本独立，内部怎么改都不影响你已经写好的算法 | **高**：它决定写算法是否省事 |
| 核心库 | 所有计算都在这里 | **高**：信号模型和指标是否正确决定论文结论是否可信 |
| 内置算法 | CBF、MVDR、MUSIC、Root-MUSIC、ESPRIT，作为对比基线 | 中：实现方式已在文档中写死，防止基线被“调弱” |
| Web 服务 + 前端 | 界面 | 中：好不好用 |
| 工作目录 | 结果以普通文件保存，不依赖竞技场也能读 | 低：按约定存放即可 |

详见：架构第 2、4、5 章。

## 6. 最重要的设计原则

这几条是整个设计的骨架。开发中如果有人提议违反它们，需要特别慎重。

| # | 原则 | 为什么重要 |
|---|---|---|
| 1 | **只有一套计算代码。** 网页和脚本调用同一个函数，Web 服务本身不做任何计算 | 保证两种用法结果一致；只需要验证一套代码的正确性 |
| 2 | **算法放在课题仓库，不放进竞技场。** 加一个算法，竞技场代码零改动 | 你的研究代码和工具各自演进，互不干扰 |
| 3 | **训练和测试用同一套信号模型。** 训练数据也由竞技场生成，并记录信号模型版本 | 学习型算法的评测结果才可信 |
| 4 | **文件是唯一的数据。** 结果是普通 JSON / npz 文件，数据库只是可以删掉重建的索引 | 结果能放进 Git、能备份、不依赖竞技场也能读 |
| 5 | **随机数完全由种子决定。** 并行或串行、中止后重跑，结果都一样 | 实验可复现；算法比较公平（同一次试验所有算法用同一份数据） |
| 6 | **每次实验自动记录全部版本信息**：配置、种子、代码 commit、未提交改动、模型哈希 | 半年后仍能说清楚某张图是怎么来的 |
| 7 | **内置基线算法的实现方式写死在文档里** | 防止开发方随意改动，让对比基线变弱或变强 |
| 8 | **一个算法出错不影响其他算法**；每个实验在独立进程中运行，卡死可以直接结束 | 长时间实验不会因为一个坏算法白跑 |

详见：架构第 1 章、第 13 章（决策记录）。

## 7. 接入一个算法有多简单

这是检验整个设计是否成功的标准。一个传统算法的完整插件大约 25 行：

```python
# Projects/fewshot-doa/algorithms/min_norm/arena_plugin.py
from arena_api import Algorithm, Estimate, ParamsModel, Param, kit

class MinNorm(Algorithm):
    id = "min_norm"; name = "Min-Norm"; version = "0.1.0"

    class Params(ParamsModel):                      # 网页表单根据这里自动生成
        grid_step: float = Param(0.1, gt=0, label="网格步长", unit="°")

    def configure(self, params, array, ctx):        # 预计算，只做一次
        ...
    def estimate(self, obs, ctx):                   # 每次试验调用：输入接收数据，输出角度
        ...
        return Estimate(angles)
```

写好后在网页上点“刷新”就能用。参数表单、出错处理、计时、指标、存档、画图都不用写。

学习型算法多一点：写三个函数（构建网络、预处理、后处理），模型加载、GPU、批量推理由竞技场完成。

详见：接口规范第 14 章（含完整示例）。

## 8. 学习型算法：云端训练、本机评测

```
本机                                        AutoDL（Linux）
课题仓库 ── git push ──────────────────▶   git clone，安装竞技场核心库
                                            用 arena.datasets 生成训练数据
                                            训练（普通 PyTorch，竞技场不介入）
                                            arena.models.export 导出模型包
arena_ws\models\ ◀── 下载模型包 ─────────
竞技场导入 → 与基线对比评测
```

要点：
- **训练过程本身不依赖竞技场**，网络、损失、优化器都是普通 PyTorch 代码。
- 竞技场只在两处参与训练：生成数据（推荐）、导出模型包（推荐）。
- 模型包只保存权重，网络结构代码在课题仓库里，由 Git 管理。
- 本机评测时，竞技场自动检查：训练用的信号模型版本是否一致、测试条件是否超出训练范围（例如训练时没有阵列误差，测试时有）。

详见：架构第 9 章，数据格式第 5、6 章。

## 9. 开发分几步走，每步你验收什么

顺序原则：**先做脚本模式，再做网页。** 计算核心正确了，网页只是界面；而且核心做好后，网页完成之前你就能用脚本开始做研究实验。

| 里程碑 | 做完后你能做什么 | 你验收时重点看 |
|---|---|---|
| M1 计算核心 | （还没有可用入口，只有测试） | 测试报告：MUSIC / ESPRIT 在高 SNR 下贴近 CRB；相干信源下不平滑的 MUSIC 失效、平滑后恢复；1000 次蒙特卡罗 × 5 个算法在 1 分钟内跑完 |
| M2 实验执行与脚本模式 | 用 Python 脚本跑完整实验，结果存进工作目录 | 自己在课题仓库里写一个简单算法，按指南接入，看是否真的只需要写 `estimate()`；同种子跑两次结果是否相同 |
| M3 图表与导出 | 脚本中出图，导出 PDF / `.mat` / LaTeX 表格 | 导出的 PDF 能否直接放进论文；`.mat` 在 MATLAB 中能否打开（含中文名） |
| M4 Web 服务 | （后台就绪，界面还没有） | 同一配置从网页接口和脚本运行，结果是否一致 |
| M5 前端 | 网页上完成全部操作 | 对照原型 `prototype/index.html` 看界面；不看文档能否配出一个实验 |
| M6 学习型算法与云端 | 在 AutoDL 训练、本机评测学习型模型 | 在 AutoDL 上实际走一遍；训练范围提示是否出现 |
| M7 场景集与排行榜（P1） | 一键跑标准场景、看排名 | 可推迟 |

M6 只依赖 M2，可以和 M3–M5 同时进行。**每个里程碑结束，用你真实的研究场景试用一次，再进入下一个。**

详见：架构第 12 章。

## 10. 开发过程中怎么判断方向对不对

**好的信号：**
- 接入一个新算法，只在课题仓库里新建一个子目录，竞技场代码一行不改。
- 给算法加一个参数，只改算法自己的 `Params`，网页表单自动出现这个参数。
- 新加一种阵列误差或一个指标，只新增一个文件。
- 训练脚本里能看到 `import arena.datasets`，而不是一份自己写的数据生成代码。
- 随便拿一个历史实验的目录，能说出它用的代码版本，并能一键重跑出相同结果。

**需要叫停的信号：**
- Web 服务（`arena/server/`）里出现了计算代码，比如自己算 RMSE、自己生成信号。
- 前端代码里出现了某个具体算法的名字或参数（如 `if algo == "music"`）。
- 内置算法的公式、空间平滑子阵大小、谱峰处理方式和接口规范第 13 章不一致。
- 用 `np.random.seed()` 或全局随机数，而不是从实验种子派生。
- 结果只存在数据库里，或用 pickle 存结果文件。
- 为了接入你的算法，需要修改竞技场的代码。

## 11. 主要风险

| 风险 | 后果 | 已有的应对 |
|---|---|---|
| 内置基线算法实现有误（如角度符号反了） | 对比结论错误，影响论文 | 接口规范 13.4 节的验收测试；Root-MUSIC / ESPRIT 符号公式已用 numpy 实测 |
| 训练和测试的信号模型不一致 | 学习型算法评测不可信 | 信号模型版本号 + 训练范围检查（架构 9.4 节） |
| 外部算法的依赖与竞技场冲突 | 某个算法装不上或跑不起来 | V1 要求同一 conda 环境；接口预留了独立进程运行的方式（V2） |
| Windows 上导出 PDF 的工具不兼容 | 不能直接出论文图 | M3 第一件事就是在本机验证（架构风险 R1） |
| 所有数据在一块硬盘上 | 硬盘坏了丢数据 | 代码在 GitHub；`Notes\` 和 `arena_ws\` 的大文件需要你另外备份 |

完整风险列表：架构第 14 章。

## 12. V1 做什么、不做什么

| V1 做 | V1 不做（但设计上预留） |
|---|---|
| 一维（方位角）、窄带、远场 | 二维 DOA、宽带、近场 |
| 均匀线阵 | 面阵、圆阵、稀疏阵、任意阵列 |
| 四类阵列误差：位置、幅相、互耦、阵元故障 | — |
| 5 个内置传统算法 + 1 个示例学习型算法 | 少样本适配 / 元学习的测试前微调 |
| 学习型算法只做推理，训练在云端 | 竞技场内训练 |
| 单次、蒙特卡罗、单变量扫描 | 两个变量同时扫描（热力图） |
| Python 算法 | MATLAB 算法、独立环境中的算法 |
| 本机单用户 | 多用户、远程访问 |

“预留”的意思是：以后加这些功能时，你已经写好的算法插件不需要修改。

## 15. 开发规范（2026-10-30 确认）

开发规范不是第 6 份设计文档，而是竞技场仓库根目录的 `AGENTS.md`。AI 编码工具每次开工都会自动读取这个文件：Claude Code 通过只有一行的 `CLAUDE.md` 引用它，Codex、Cursor 直接读取。代码风格写进工具配置（根目录的 `pyproject.toml`、`.pre-commit-config.yaml`），提交前自动检查，不靠文字约束。

| 方面 | 约定 |
|---|---|
| 分支与审查 | 每个里程碑一个分支。AI 在分支上小步提交，完成后写里程碑报告；**由你按第 9 节验收后合并**，AI 不能自己合并 |
| 提交信息 | `feat(algorithms): 新增 TLS-ESPRIT` 这种格式：英文类型前缀 + 中文描述 |
| 注释和文档字符串 | 中文；变量名、函数名、文件名用英文 |
| 代码检查 | ruff 负责格式化和检查，mypy 检查类型，pytest 跑测试；提交前自动运行，大于 1 MB 的文件提交不了 |
| 硬性规则 | 把第 10 节“需要叫停的信号”写成 13 条规则，其中禁用全局随机数等由工具直接拦截 |
| 里程碑报告 | 固定 6 节：完成内容、怎么验收、测试结果、与设计的偏离、需要你决定的问题、已知问题。**你主要通过它把握进度** |
